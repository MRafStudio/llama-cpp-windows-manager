# Подпись релизов Windows

Последняя проверка: 2026-08-15

Доверенные релизы Windows должны быть подписаны Authenticode и снабжены меткой
времени (timestamp) до загрузки. Неподписанные общественные релизы должны везде,
где на них даются ссылки, быть описаны как неподписанные. Скрипты релиза
поддерживают подпись сертификатом, уже доступным в хранилище сертификатов
Windows:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\publish-app.ps1 -CertificateThumbprint "<cert-thumbprint>" -RequireSigned
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\build-installer.ps1 -CertificateThumbprint "<cert-thumbprint>" -RequireSigned
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-release-gate.ps1 -IncludePublish -IncludeInstaller -CertificateThumbprint "<cert-thumbprint>" -RequireSigned
```

Когда `scripts/build-installer.ps1 -SkipPublish -RequireSigned` повторно
использует существующую папку публикации, скрипт проверяет, что опубликованный
исполняемый файл уже подписан, до компиляции и подписи установщика.

Исполняемый файл Manager встраивает `llwmctl.exe`, `AGENTS.md`, `agent.md`,
`docs/CONTROL_API.md`, `LICENSE` и уведомления третьих сторон/.NET, затем
восстанавливает проверенные копии сайдкаров при запуске. Любое изменение этих
операторских документов поэтому требует свежей публикации перед подписью;
копирование отредактированного Markdown рядом с уже подписанным исполняемым
файлом не обновляет встроенный контракт релиза, и следующий bootstrap может
восстановить встроенную версию.

Необязательные доверенные подписанные сборки используют
`.github/workflows/release.yml` через ручной запуск (manual dispatch). Настройте
защищённую среду `release` с секретами `WINDOWS_SIGNING_PFX_BASE64` и
`WINDOWS_SIGNING_PFX_PASSWORD`. Рабочий процесс отказывается собирать
подписанные артефакты без обоих секретов, импортирует сертификат только для
задания, запускает контроль релиза с `-RequireSigned` и удаляет
импортированный сертификат после. Теги версий не запускают это дополнительное
задание, поэтому репозитории без секретов подписи могут публиковать корректно
помеченные неподписанные релизы без падающей проверки статуса. Обычный CI для
pull-request'ов по-прежнему использует неподписанный смоук-тест упаковки,
потому что ненадёжные PR никогда не должны получать учётные данные подписи.

Рабочий процесс закрепляет действия GitHub по коммиту и устанавливает
фиксированную версию Inno Setup до импорта сертификата подписи. Держите всю
настройку пакетов/инструментов до импорта сертификата, чтобы код стороннего
установщика никогда не выполнялся, пока закрытый ключ доступен заданию.

## Бесплатные варианты

- **Бесплатно и публично полезно для подходящего OSS:** подайте заявку в
  SignPath Foundation на подпись кода для открытого ПО. В случае одобрения
  используйте их рабочий процесс подписи для артефактов релиза.
- **Бесплатно, но не имеет публичного доверия:** самоподписанные сертификаты
  полезны для локального тестирования и корпоративных сред, где сертификат
  развёртывается в доверенные хранилища. Они не убирают предупреждения
  SmartScreen или публичного доверия для обычных пользователей.
- **Бесплатная целостность, но не доверие Authenticode:** публикуйте
  файлы-компаньоны `.sha256` и происхождение релиза GitHub. Это помогает
  пользователям проверять загрузки, но не заменяет подпись кода Windows.

## Правило доверенного релиза

Не описывайте релиз как подписанный, доверенный или усиленный для продакшена,
если не выполнены условия:

1. `LlamaCppWindowsManager.exe` подписан до компиляции установщика.
2. `LlamaCppWindowsManager-Setup-<version>-win-x64.exe` подписан.
3. `LlamaCppWindowsManager-win-x64.zip` создан из подписанного содержимого.
4. У каждого загруженного двоичного файла/архива есть соответствующий
   артефакт-компаньон `.sha256`, созданный после подписи.
